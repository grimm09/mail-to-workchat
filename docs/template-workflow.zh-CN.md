# 回复模板工作流

[English](template-workflow.md) | **简体中文**

## 状态模型

```text
首次匹配邮件
  -> 模板提案
  -> needs-review（待审查）草稿
  -> 人工编辑提案
  -> 明确批准
  -> 已批准模板
  -> 兼容的已有待审查草稿变为 ready
  -> 后续匹配邮件生成 ready（可用）草稿
```

系统不会发送这些回复。使用者打开 Markdown 草稿，核对后将主题和正文复制到邮件客户端。

## 内置占位符

每个模板都可以使用：

- `{subject}`
- `{sender_name}`
- `{sender_email}`
- `{account_id}`
- `{account_label}`
- `{received_at}`

配置的命名字段（如 `{case_id}`）在提取成功后同样可用。

只接受简单名称。`{object.attribute}`、`{items[0]}`、`{subject!r}` 或 `{subject:>2000000}` 等表达式会被拒绝。
展开后的输出也有大小限制。

## 生成提案

规则包含 `reply_body_seed` 时，该内容会成为初始回复提案。为空时，本地生成器会生成保守的韩文确认收悉草稿，
其中包含邮件主题和成功提取的字段。这是确定性的本地起始模板，不是 AI 理解邮件，也不是自动从邮件中学习。
本版本不会将邮件发送给 AI 服务商。

`reply_language` 和模板的 `language` 只是语言标记，不会自动翻译。要生成英文或中文草稿，应提供对应语言的非空种子正文，
或审查并安装一种选定语言的示例模板。原有韩文兜底内容保持不变，详见[语言与示例](languages.zh-CN.md)。

生成的提案不包含原邮件正文或实际捕获的字段值，而是保存匹配表达式和占位符，以降低将个人数据写入可复用文件的可能性。

## 批准

编辑 `.runtime/proposals/<rule-id>.toml`，再次预览后批准。批准操作将通过校验的内容复制到本地配置的模板目录，
并设置 `approved = true`。

除非明确传入 `--overwrite`，否则不会覆盖现有的已批准文件。不要将覆盖当作常规更新方式；应先审查差异。

启用可选个人交互层后，管理员可以在群中提交回复主题／正文更新。指令会创建待确认变更和差异预览；
另一次 `模板确认` 指令才会应用变更，同时保存不可变的本地版本供回滚使用。群内更新不能修改匹配表达式或字段提取规则。

CLI 批准只会刷新已保存匹配／提取指纹与已批准模板一致的待审查事项。交互式 `回复` 指令也可执行这种兼容刷新。
没有该指纹的旧记录，或匹配／提取规则已变化的模板，需要在本地重新预览原邮件后人工复制。
系统不会完整保存原邮件正文，因此不能从片段中猜测新的字段。

模板变更后，已经 ready 的草稿仍作为不可变的历史快照保留。新内容生成新的内容寻址文件，
而不会覆盖其他预览或事项的草稿。模板确认使用写锁、拒绝过期提案，并记录 `applying` 意图；
进程中断后，请重试同一个变更 ID。使用本地 `--overwrite` 或编辑器修改已批准模板之前，
应停止相关进程并处理完中断的确认操作。

## 匹配规则

没有已批准模板匹配时，进入提案流程；恰好一个模板匹配时，渲染该模板；多个模板同时匹配时，因存在歧义而停止生成。
应收紧发件人／主题／正文匹配表达式，而不是依赖模板文件顺序。
